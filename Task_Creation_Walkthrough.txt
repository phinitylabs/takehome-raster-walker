# Takehome: Improving an AI Agent's Pass Rate on a Hardware Verification Task

## Background

We build evaluation tasks for AI coding agents. In this task the agent is
given a hardware module's specification and must write a **self-checking
SystemVerilog testbench** for it. The agent never sees any implementation of
the module. Its testbench is then graded by running it, unmodified, against
several hidden implementations: one that conforms to the specification
exactly, and a set of defective ones (each containing a single planted bug).
The testbench passes grading only if it passes the conforming implementation
AND detects (fails) every defective one. It is like grading a professor's
exam key rather than a student's answer: the key must accept a correct
solution and catch every wrong one.

We also need a golden testbench that acts as the reference answer for this
task: a testbench that follows the specification exactly, passes the
conforming implementation, and detects all of the defective ones.

Your job in this takehome is to **create the golden testbench, analyze how
an AI agent fails at this task, then modify the specification so the agent
succeeds more often — raising its pass rate into a target band, without
giving the answers away**.

You are given a task where an AI agent (Claude Sonnet) achieves
approximately **20% pass rate** across 10 independent attempts. Your goal
is to modify the prompt/specification so that the agent's pass rate rises
to **between 50% and 80%** (out of at least 10 runs), while the specification
remains an honest, self-contained module spec: you may clarify, illustrate,
and re-emphasize, but the document must still read as a specification — not
as a list of the grader's test cases.

## Section 1: Understanding the Task (~30 min) (Terminal 1)

The module under test is `raster_walker`: a first-octant raster line walker.
Given extents `(dx, dy)` with `dy <= dx`, it streams the `dx` unit steps
(E or NE) of the closest-lattice-point walk from `(0,0)` to `(dx,dy)` over a
stalling `step_valid/step_ready` handshake, with `start/busy/done` traversal
control and a synchronous reset. Read `docs/spec.md` carefully — the step
direction rule, the acceptance/timing conventions, and the reset semantics
are all normative.

The agent's job (and yours, in Section 2) is not to implement this module —
it is to write the testbench that verifies it. The agent receives:

| File                       | Purpose                                                        |
| -------------------------- | -------------------------------------------------------------- |
| `prompt.txt`               | Instructions: the deliverable and its requirements (verdict protocol, compile contract) |
| `docs/spec.md`             | Detailed specification of raster_walker's behavior             |
| `sources/raster_walker.sv` | A non-functional stub with the correct ports (replaced during grading; the agent may implement it locally to exercise its testbench) |
| `tb/tb_raster_walker.sv`   | Testbench skeleton — the agent must complete this file         |

The agent does **not** see any real implementation or the grading harness.
It reads the prompt and spec, writes a testbench (usually implementing its
own version of the module to test against), and is then graded.

### Branch structure

The repo has three important branches:

| Branch                   | What's on it                                                                                    |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| `raster_walker_baseline` | The starting point: spec + stub + testbench skeleton. **This is what the agent sees.**          |
| `raster_walker_test`     | Same as baseline, plus the grading harness (`tests/test_tb_raster_walker.py`) and the hidden implementations (`grading/rtl/golden.sv` + `grading/rtl/mut_*.sv`). Used for grading. |
| `raster_walker_golden`   | Same as baseline, but with the complete golden testbench in `tb/tb_raster_walker.sv`. (To be implemented by you) |

To look at the grading harness and the implementations it grades against:

```bash
git checkout raster_walker_test
cat tests/test_tb_raster_walker.py
ls grading/rtl/
```

`golden.sv` is the conforming implementation. Each `mut_*.sv` is a defective
variant that violates exactly one clause of `docs/spec.md` — the file names
hint at the planted bug. A testbench passes grading only if `golden.sv`
passes it and every `mut_*.sv` fails it.

To return to the baseline (what the agent starts with):

```bash
git checkout raster_walker_baseline
```

Take time to read `docs/spec.md` and `prompt.txt`. Understand the step
sequence definition (including what happens when two lattice points are
equally close), the acceptance predicate, the registered-output timing
rules, the stall/persistence obligations, and the reset behavior in every
phase — the defective implementations live exactly in those corners.

## Section 2: Creating the Golden Testbench (~2-3 hr)

Based on the specification, create the golden testbench in
`tb/tb_raster_walker.sv` and push it on the `raster_walker_golden` branch.

Follow the verdict contract in `prompt.txt` exactly: the testbench prints a
line containing `TB_PASS` and calls `$finish` if and only if every check
passed, and prints a line containing `TB_FAIL` and terminates with
`$fatal(1)` on the first failure.

A useful workflow: implement your own `raster_walker` in
`sources/raster_walker.sv` (it is a stub on every branch and is never
graded) so you can run your testbench locally, then verify against the real
grading set (Section 3).

```bash
git checkout raster_walker_golden
# (implement tb/tb_raster_walker.sv per docs/spec.md and prompt.txt)
git add tb/tb_raster_walker.sv
git commit -m "raster_walker: golden testbench"
git push origin raster_walker_golden
```


You should see a failure on `test_conforming_implementation_passes`. Now,
temporarily swap in your golden testbench and re-run:

```bash

uv run pytest tests/test_tb_raster_walker.py -q
```

This should pass all checks: the conforming implementation passes your
testbench, and every defective implementation is detected. Restore the
baseline skeleton before continuing:

```bash
git checkout origin/raster_walker_test -- tb/tb_raster_walker.sv
```

## Section 4: Analyzing Agent Behavior (1 hour)

Here are the results of 10 runs of Claude Sonnet 4.5 attempting this task
with the current spec:

**[View the 10 runs here](https://hud.ai/jobs/b1110e9066714432bf1cbd1dbf32f81f)**

The agent achieves approximately **20% pass rate**.

Open several **failing** runs (and any passing ones) and carefully read
through the agent's work. Pay attention to:

- How does the agent decide what the module should do? It cannot see any
  implementation — so where does its expected behavior come from: the spec
  text, or its prior knowledge of similar modules?
- The agent almost always writes its own implementation of the module to
  exercise its testbench. Compare that implementation, and the testbench's
  expected values, against the spec text. When both contain the same
  mistake, its self-tests pass while grading fails — find the runs where
  this happened and identify the exact spec clause involved.
- Which grading failures are "testbench rejects the conforming
  implementation" (the agent's oracle is wrong) versus "a defective
  implementation survived" (the agent never tested that corner)? The
  harness output names the variant that survived — map each surviving
  variant back to the spec clause it violates and ask why the agent's
  stimulus never exercised it.
- What does the agent test on its own initiative (randomized traversals,
  simple handshake tests) and what does it systematically skip (boundary
  requests, resets outside idle, cycle-exact timing)?

Understanding *why* the agent fails is the key to this takehome. The agent
is not incapable — there are specific, identifiable properties of the
specification that cause its oracle to diverge from the spec, and specific
blind spots in the corners it chooses to test. Your analysis of these
properties will directly inform how you modify the spec. We strongly
recommend working backwards — look at the final testbench the agent
created at the end of the trace, and at the scratch implementation it
tested against, and compare both to the specification text. You can find
the final files in HUD by scrolling to the bottom of the trace and looking
through the code window in the final cell (on the left side of the
transcript).

## Section 5: Modifying the Specification (~1–2 hrs)

Your goal is to modify `docs/spec.md` (and/or `prompt.txt`) so that the
agent's pass rate rises to **between 50% and 80%** — while keeping the
document an honest specification.

**The rules (hard constraints — submissions violating them are rejected):**

- The document must remain a **specification of the module**, complete and
  self-consistent. You may clarify, illustrate, restructure, and add worked
  examples or derivable corollaries; you may not turn it into a checklist
  of the grader's test cases (e.g., pasting the mutant list or per-variant
  instructions like "also test X against implementation Y").
- Do not weaken or remove normative requirements: the same behaviors must
  remain specified, and the hidden grading set is not modified.
- Your own golden testbench (Section 2) must still pass the grading harness
  after your changes.
- Do not modify the grading harness or the `grading/rtl/` implementations.

**What you *may* do — make the correct reading unavoidable and the critical
corners salient:**

- Add worked examples that pin a derivation the agent gets wrong (a single
  well-chosen example can eliminate an entire class of oracle errors).
- Promote easily-missed clauses from low-prominence locations (a port-table
  cell, a subordinate sentence) into prominent, structured statements.
- Add derivable corollaries, cross-references, and self-check anchors that
  let the agent validate its own oracle before trusting it.
- Add explicit verification guidance to `prompt.txt` (e.g., "test every
  boundary and reset case the spec names") — guidance about *thoroughness*
  is fair; naming specific planted bugs is not.
- Consider *how the agent verifies itself*: a change only raises the pass
  rate durably if it either corrects the agent's oracle (so it stops
  false-failing the conforming implementation) or drives its stimulus into
  corners it currently skips (so it starts killing the surviving variants).

Principles to keep in mind:

- The agent is an AI model, not a human engineer. What clarifies for a
  human may be ignored by an agent — and vice versa. Target the specific
  behaviors you observed in the traces (Section 4). Blind additions rarely
  move the number.
- Each change should map to an observed failure: "in runs 3, 7, and 12 the
  agent's oracle resolved X the wrong way; this example pins X."

Each time you make a change, you should test it by running on HUD
(Section 6).

## Section 6: Running on HUD (~30 min) (Terminal 2)

Now come to Terminal 2 for setting up the framework:

**Register the problem.** Open `src/hud_controller/problems/basic.py` and append:

```python
PROBLEM_REGISTRY.append(
    ProblemSpec(
        id="raster_walker",
        description="""Write a self-checking SystemVerilog testbench for the module
`raster_walker` specified in docs/spec.md.

Your testbench must be able to determine, on its own, whether an
implementation of raster_walker conforms to docs/spec.md: when it runs
against a conforming implementation, every check must pass; an
implementation that deviates from the specification in any observable way
must fail at least one check. Be thorough — exercise and check every
normative behavior in the specification, including every boundary,
simultaneity, timing, and reset rule it states, not just typical
operation.

Requirements:
- Complete tb/tb_raster_walker.sv. The top-level module must remain
  `tb_raster_walker`, and the file must stay self-contained: it may not
  read other files or depend on plusargs.
- Compatible with Icarus Verilog (-g2012). No concurrent SystemVerilog
  Assertions (immediate procedural checks are fine). No DPI.
- The testbench instantiates the DUT as module `raster_walker` with the
  default W = 8 and exactly the ports in the spec, taking the DUT from
  sources/raster_walker.sv; the pair must compile and run as:
      iverilog -g2012 -s tb_raster_walker -o sim.vvp \\
          sources/raster_walker.sv tb/tb_raster_walker.sv
      vvp sim.vvp
- Verdict contract:
  - if and only if every check passed: print a line containing TB_PASS,
    then call $finish;
  - on the first failed check: print a line containing TB_FAIL, then
    terminate with $fatal(1);
  - never print both TB_PASS and TB_FAIL in the same run;
  - the run must always terminate itself and reach a verdict, even against
    a badly broken implementation: use an explicit watchdog that prints
    TB_FAIL rather than letting the simulation hang, and keep total
    simulated cycles well under one million so a run finishes within a few
    seconds.
- The provided sources/raster_walker.sv is a non-functional placeholder
  with the correct interface; it is not part of the deliverable. You may
  edit it locally (for example, write your own implementation of the spec)
  to exercise your testbench.
- Do not modify or create files outside sources/ and tb/. Files your
  simulation writes at run time (such as VCD dumps) are not covered by
  this rule; do not include $dump* calls in the submitted testbench.

Deliverable: the completed tb/tb_raster_walker.sv.
""",
        difficulty="hard",
        base="raster_walker_baseline",
        test="raster_walker_test",
        golden="raster_walker_golden",
        test_files=["tests/test_tb_raster_walker.py"],
    )
)
```

The branch names (`base`, `test`, `golden`) must exactly match the branches in your fork. Since forking preserves all branches, these already exist.

**Point the Dockerfile at your fork.** Open `Dockerfile` and find the `REPO_URL` line (near line 103):

```dockerfile
ARG REPO_URL=https://github.com/hud-evals/example-verilog-codebase.git
```

Change it to:

```dockerfile
ARG REPO_URL=https://github.com/<your-github-username>/takehome-raster-walker.git
```

Since your fork is public, Docker can clone it without any authentication token.

### After each spec modification

**1. Update the branches.** From your forked repo (Terminal 1 `takehome-raster-walker`), commit your spec change and push to all three branches — baseline, test and golden:

**2. Rebuild the Docker image.** Back in the (Terminal 2) framework repo, first increment the cache-buster in the `Dockerfile` so Docker pulls fresh code from your fork (find the `ENV random=random6` line near `REPO_URL` and change the number, e.g. `random7`, `random8`, etc.). Then build:




```bash
uv run python run_eval.py --ids raster_walker --agent claude --model claude-sonnet-4-5 --max-steps 100 --group-size 10
```

`run_eval.py` starts a fresh Docker container per rollout, runs the agent, grades each attempt, and prints progress plus a job URL like `https://hud.ai/jobs/<job-id>`. Open that link to inspect individual rollouts.

Iterate until you achieve a 50–80% pass rate.
